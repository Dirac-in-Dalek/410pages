# 문자열 순서 키 전환

상태: 사용자 선택 2번과 후속 진행 승인에 따라 로컬 검증과 운영 DB 마이그레이션을 완료했다. 앱 배포 결과는 연결된 PR과 배포 실행 보고에서 확인한다.

## 바뀌는 것

- citations와 chapter_blocks에 `order_key text COLLATE "C"`를 추가한다. 기존 `created_at_sort`와 작성일·본문·페이지·메모·강조·단계를 수정하지 않는다.
- 기존 숫자를 순서가 보존되는 IEEE754 바이트 문자열로 매핑한다. JavaScript와 PostgreSQL 변환 결과를 비교한다. 숫자가 같은 기존 항목은 이전을 중단하여 임의의 순서를 만들지 않는다.
- 새 삽입·이동은 Rocicorp fractional-indexing 3.2.0 기반 jittered-fractional-indexing 1.0.1로 문자열 사이의 새 키를 만든다. 두 창이 같은 간격에 입력할 때 충돌 확률을 낮추기 위해 암호학적 난수 64비트를 사용한다. 확률적 회피만 믿지 않고 DB 중복 검사와 제한된 재시도를 추가한다.
- 길어진 키를 일반 B-tree 유일 인덱스에 직접 넣지 않는다. 책 ID와 키 해시를 사용하며 두 테이블 사이의 중복은 책별 잠금과 트리거로 검사한다. 해시 충돌도 오류로 처리하며 다른 순서값으로 오인하지 않는다.
- 조회·미리보기·계층 계산·저장·드래그·키보드 이동·실패 초안·출처 변경에서 같은 순서 키를 사용한다. 키가 없는 기존 로컬 초안은 기존 숫자 위치를 변환해 복구한다.
- 일괄 출처 변경은 인용문별 키와 변경 전 위치를 함께 보내는 단일 DB 함수로 처리한다. 중간 실패는 전부 롤백하고, 다른 창이 위치를 바꾼 오래된 요청은 재조회하도록 거절한다.
- 기존 책·저자 병합도 유지한다. 원래 두 책에서 같았던 키가 충돌하면 해당 이동 항목의 키만 가까운 문자열 사이로 조정한다. 실제 반영된 키를 병합 응답과 화면 캐시에 함께 반영한다.

## 운영 적용 전에 확인할 것

1. 전체 migration을 트랜잭션으로 적용한다. 먼저 책별 기존 유효 숫자의 동률과 비정상 숫자가 없는지 확인한다. 초기 검사에서 중단하면 임의로 데이터 보정하지 않는다.
2. 책별 통합 순서의 ID 목록과 기존 필드의 검증값을 이전 전후 비교한다. 실제 Supabase 환경의 권한·트리거·인덱스도 확인한다.
3. 새 함수는 security invoker이며 로그인 사용자와 책 소유권을 확인한다. 기존 RLS를 비활성화하지 않는다.
4. 새 스키마를 먼저 적용하고 새 앱을 배포한다. 배포 전 잠깐의 전환 구간이나 오래 열린 구버전 화면에서는 숫자만 쓰는 저장·이동이 명시적으로 거절된다. 조용히 잘못된 순서로 저장하지 않도록 한 호환성 경계다. 새로고침 후 새 앱을 사용한다.
5. 롤백은 구버전 앱만 재배포하는 방식으로 하지 않는다. 새 문자열 위치로 작성한 기록의 순서를 구버전 숫자만으로 표현할 수 없기 때문이다. 기존 숫자 필드를 보존해도 즉시 앱 롤백이 안전하다는 뜻은 아니다.

## 검증 층

- 순수 함수: 인접한 부동소수점 값 사이 삽입, 1,000회 반복 삽입, 혼합 legacy/key 순서, 계층 계산.
- 격리 PostgreSQL(PGlite): migration의 기존 데이터 보존, JS/SQL 매핑 일치, 1,000개 저장, 긴 키, 소유권, 중복·구버전 쓰기 거절, 동률 실패 시 전체 롤백.
- API: 충돌 응답 재시도, 응답 키 반영, 출처 이동과 초안 복구.
- 실제 PostgreSQL 다중 연결의 잠금 경합과 운영 계정 저장은 별도 확인이 필요하다. PGlite의 단일 연결 검사를 이를 검증한 것으로 보고하지 않는다.
