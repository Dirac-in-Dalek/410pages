# 중간 연속 기록의 정렬 간격 복구안

상태: 채택하지 않은 이전 제안. 사용자는 이후 문자열 순서 키 방식(2번)을 선택했다. 현재 구현·운영 적용 계획은 [문자열 순서 키 전환](./2026-09-27-string-book-order.md)을 따른다. 이 문서의 숫자 재배치나 운영 DB 변경은 실행하지 않았다.

## 확인한 결함

인용문·챕터의 `created_at_sort`는 double precision이다. 중간 삽입은 양옆 값의 평균을 쓰고, 다음 기록은 방금 저장한 항목 뒤에 삽입된다. 따라서 같은 구간의 남은 간격이 계속 절반으로 줄어든다. 실제 타임스탬프 크기의 값과 약 0.9 간격에서 12회 저장 후 13번째가 차단되는 것을 격리 브라우저에서 재현했다. 작성 중인 내용은 남아 있었다.

현재 두 값 사이에 표현 가능한 숫자가 하나도 없으면 클라이언트 계산식만으로 새 위치를 만들 수 없다. 작은 고정 증가량이나 같은 값 재사용은 각각 한계를 늦추거나 순서를 모호하게 할 뿐이다.

## 승인받을 변경

대상은 저장하려는 사용자의 해당 책 한 권이다. 정렬 간격이 부족할 때만 챕터와 인용문을 합친 현재 순서대로 내부 정렬값을 일정 간격으로 재배치하고, 요청한 새 항목을 같은 트랜잭션에서 삽입한다. 전체 서재 일괄 변경이나 별도 소속 필드 추가는 하지 않는다.

- 기존 항목의 ID·순서·챕터 단계·소속·본문·페이지·작성일·메모·강조는 유지한다. 기존 행에서 바꿀 값은 `created_at_sort`뿐이다.
- DB 함수에서 로그인 사용자와 책 소유권을 검증한다. 브라우저의 사용자 ID만 믿지 않는다.
- 위치 숫자 대신 앞·뒤 항목의 ID와 현재 순서 버전을 기준으로 삽입한다. 복구 전의 오래된 숫자를 뒤늦게 저장하지 않도록 생성·이동·재시도 경로를 함께 검토한다.
- 같은 책에 대한 동시 변경을 직렬화하고, 오래된 화면에서 보낸 요청은 재조회·재시도하거나 명시적으로 거절한다. 순서가 달라진 상태에서 추측하여 저장하지 않는다.
- 재배치와 새 항목 저장 중 하나라도 실패하면 전체를 롤백한다. 재배치 일부만 성공한 상태를 남기지 않는다.
- 서버가 확정한 위치를 목록·낙관 표시·책별 입력 초안에 함께 반영한다. 저장 대기 중인 인용문과 로컬 실패 초안을 누락하지 않는다.
- 함수 설치가 곧 기존 데이터 일괄 변경을 의미하지 않도록 한다. 운영 적용 전 대상 스키마와 권한을 읽기 전용으로 확인한다.

## 검증·복구 기준

1. 격리 DB에서 실제 타임스탬프 크기와 이미 소진된 간격을 준비한다.
2. 같은 중간 구간에 100개 이상을 연속 저장하고 재조회해 순서·소속·기존 필드 보존을 비교한다.
3. 다른 사용자 책 접근, 두 탭 동시 저장, 순서 변경 후 도착한 오래된 요청, 재시도·응답 유실을 검사한다.
4. 재배치 뒤 새 항목 저장 실패를 주입하여 정렬값까지 전부 롤백됐는지 확인한다.
5. 운영 적용 전후 대상 행의 ID·기존 정렬값과 보존 필드 검증값을 확보한다. 이미 후속 기록이 생겼다면 오래된 정렬값을 그대로 덮어쓰는 복구는 하지 않는다.

이 변경은 클라이언트 UI 수정만으로 배포할 수 없다. DB 함수와 위치를 쓰는 경로의 호환성을 격리 검증한 뒤, 운영 DB 적용·앱 배포 순서를 정해야 한다.
