# Supabase 데이터베이스 점검 — 2026-10-08

현재 공개 키로 실제 인증·데이터 API에 연결할 수 있다. 비로그인 조회에서 점검한 주요 테이블의 보이는 행은 0개이고 이메일 확인이 활성화되어 있다. 저장소의 후속 마이그레이션은 사용자 간 연결을 제한하고, 격리 PostgreSQL의 두 연결에서도 책 순서 중복을 막았다.

우선 개선할 부분은 **재구성 가능한 스키마, 조회 누락 방지, 저장의 원자성, 여러 기기의 편집 충돌**이다. 운영 DB의 전체 권한·인덱스·백업·인증 설정을 조회할 관리 연결은 이번 환경에 없으므로, 운영 전체가 안전하다는 판정은 아직 하지 않는다.

## 범위와 증거

- 기준 커밋: `92717c3591f8b65b4dfaee9a3f1ad1ae15bdf580`.
- 실제 대상: `yyfapuwgvimbjsebfifb.supabase.co`. 환경 키는 공개 publishable 키이며 관리자 키는 아니다.
- 운영 요청은 GET/HEAD만 사용했다. 실제 계정 생성·로그인·저장·설정 변경·마이그레이션은 실행하지 않았다. 본문·메모·이메일 등 개인 기록은 조회하지 않았다.
- 로컬 검증: PostgreSQL 17.11, 외부 네트워크·공개 포트·호스트 마운트 없는 일회성 Docker 컨테이너. 모든 행은 가짜 데이터이고 종료 시 컨테이너와 데이터가 제거된다.
- 재현 도구: [scripts/qa-database.py](../../scripts/qa-database.py).
- 운영 점검 도구: [supabase/audit/health-check.sql](../../supabase/audit/health-check.sql). 한 SELECT가 메타데이터·집계만 담은 JSON 하나를 반환한다.

## 개선 우선순위

P1은 데이터 누락·덮어쓰기·복구 실패를 우선 방지하는 작업, P2는 무결성·운영 편의·성능 개선이다. 아래의 로컬 재현 결과를 현재 운영 데이터의 오염이나 유출로 해석하지 않는다.

### P1 — 운영 상태를 재구성할 수 있는 기준 스키마가 없다

[supabase_schema.sql](../../supabase_schema.sql)은 현재 API에 필요한 `citations.author_id`, `citations.page_sort`, `books.memo`, 저자 폴더와 여러 RPC·트리거 정의를 완전히 포함하지 않는다. 이 파일을 새 DB에 적용하는 것은 성공하지만 앱 API 필드 조회가 실패한다. 이어서 저장소의 마이그레이션을 순서대로 적용하면 `20260827070649_enforce_tenant_owned_relationships.sql`에서 `citations_author_id_fkey` 부재로 SQLSTATE `42704`가 발생한다. 트리거 권한 강화 파일이 요구하는 과거 함수 정의도 기준 스키마에 없다.

기준 SQL만 적용한 격리 DB에서는 자신의 책·댓글·프로젝트를 다른 계정의 저자·인용문에 연결하는 쓰기가 허용됐다. 후속 소유권 마이그레이션을 적용하면 FK 또는 RLS 오류로 모두 거절된다. **현재 운영에서 이 취약점이 존재한다는 증거는 아니다.** 잘못된 초기 설치·복구 경로가 보호 규칙을 빠뜨릴 수 있다는 재현이다.

개선: 운영 카탈로그와 마이그레이션 이력을 읽어 완전한 기준 스냅샷을 만들고, 신규 프로젝트 생성과 기존 프로젝트 업그레이드를 구분한다. CI에서 빈 DB→기준 스키마→후속 변경의 재구성을 검증한다. 이전 마이그레이션을 운영에서 일괄 재실행하거나 데이터가 있는 테이블에 누락 필드를 임의 추가하지 않는다. README도 현재 SQL을 스키마 자료로 설명하고 있어, 이 점검은 지원되는 자동 설치 경로가 이미 존재한다고 전제하지 않았다.

### P1 — 목록 조회에 페이지 구분이 없어 큰 서재가 잘릴 수 있다

[citationApi.ts](../../shared/api/citationApi.ts)의 `fetchCitations`, [bookApi.ts](../../shared/api/bookApi.ts)의 `fetchBooks`, [projectApi.ts](../../shared/api/projectApi.ts)의 `fetchProjects`, 저자·폴더·장 조회에 `.range()` 기반 순회 또는 서버 페이지 구분이 없다. PostgREST의 행 제한에 도달하면 오류 없이 일부 행만 받아 전체 데이터로 취급할 수 있다. Supabase의 통상 기본 제한은 1,000행이며 **이 프로젝트의 실제 제한과 현재 누락 여부는 아직 미확인**이다. 2026-09-27 문서에는 당시 인용문 867개가 기록되어 있다. 관련 프로젝트 연결·댓글 임베드의 별도 제한도 확인해야 한다.

개선: 안정된 `(created_at,id)` 커서 또는 명시적 범위·정렬로 전체 로드 계약을 보장하고, 큰 목록은 검색·필터·개수를 서버에서 처리한다. 책 목록에서 모든 메모를 처음부터 가져오는 흐름과 인용문마다 모든 댓글을 임베드하는 흐름도 비용을 측정한다. 설정의 행 제한만 올리는 방식은 장기 해결이 아니다.

### P1 — 일부 출처 생성은 원자적 RPC를 우회한다

저자·책 생성 화면은 `get_or_create_author` / `get_or_create_book` RPC를 사용하지만, [citationApi.ts](../../shared/api/citationApi.ts)의 `resolveCitationSource`는 조회 후 직접 INSERT를 수행한다. DB에 일반 저자 이름·책 제목의 유일 제약이 없어 두 요청이 동시에 같은 출처를 생성할 수 있다.

격리 DB에서 같은 이름의 RPC 4개를 동시에 실행하면 저자 ID가 하나였지만, 직접 INSERT 4개는 모두 성공하고 서로 다른 ID 4개를 만들었다. 직접 삽입은 실제 운영 API에서 실행하지 않았다.

개선: 인용문 저장과 출처 변경도 공통 원자적 출처 해석 경로를 사용한다. 본인 저자와 표시 이름 갱신은 전용 규칙을 유지한다. 기존 중복 수를 먼저 집계하고 정책을 정한 뒤 필요하면 정규화한 이름·제목의 유일 제약을 추가한다. 계정 변경 검사를 각 경로에서 일관되게 적용하고 프로필 조회 오류를 조용히 대체 이름으로 바꾸지 않는다.

### P1 — 여러 기기의 메모 저장은 오래된 편집으로 덮어쓸 수 있다

[bookApi.ts](../../shared/api/bookApi.ts)의 `updateBookMemo`는 책 ID와 소유자만 확인하고 메모 전체를 UPDATE한다. [BookMemoPanel](../../features/archive/ui/BookMemoPanel.tsx)은 한 편집기 안의 요청을 직렬화하지만 다른 탭·기기의 요청에는 버전 검사가 없다.

격리 DB에서 첫 클라이언트 수정과 오래된 두 번째 클라이언트 수정이 모두 성공했고, 최종 값은 두 번째 클라이언트의 내용이었다. 로컬 초안은 실패 복구를 돕지만 이 충돌을 감지하지 못한다.

개선: DB 관리 `revision` 또는 `updated_at`으로 조건부 갱신을 수행한다. 읽은 버전과 다르면 성공으로 처리하지 않고 서버 값과 로컬 초안을 모두 보존한다. 인용문·댓글 편집에도 같은 충돌 계약이 필요한지 함께 검토한다. 성공한 마지막 저장을 자동 병합이라고 표현하지 않는다.

### P2 — 프로젝트 순서 저장은 중간에 일부만 반영될 수 있다

[projectApi.ts](../../shared/api/projectApi.ts)의 `reorderProjects`는 프로젝트마다 UPDATE를 `Promise.all`로 보낸다. 한 요청이 실패해도 이미 완료한 다른 요청은 롤백되지 않는다. 저자·책 순서는 [atomic_library_reorder](../../supabase/migrations/20260901030323_atomic_library_reorder.sql)의 단일 RPC를 사용하므로 처리 수준이 다르다.

개선: 프로젝트 순서도 소유자·중복 ID·대상 집합을 검증하는 단일 RPC로 저장한다. 동시 순서 변경을 허용할지, 이전 버전을 검사해 오래된 요청을 거절할지도 계약에 포함한다.

### P2 — 사용자 소유권 외의 데이터 불변식이 부족하다

소유권 복합 FK는 다른 계정 연결을 차단하지만, 같은 계정의 책과 인용문 저자가 서로 다른 경우까지 제한하지 않는다. 격리 DB에서 이런 저장이 성공했다. `protect_self_author`는 본인 저자의 삭제·정체성 제거를 막지만, 두 번째 `is_self=true` 저자의 INSERT는 허용한다. 이름·제목·장 제목의 공백 및 JSON 형태 검증도 테이블별로 일관되지 않다.

개선: 실제 집계를 먼저 확인하고 본인 저자 1명, 책과 인용문의 저자 일치, 유효한 입력의 DB 제약을 명확히 한다. 복구·병합에서 데이터를 자동 삭제하지 않는다. 프로필 `username`의 전역 유일성은 표시 이름의 제품 목적에 맞는지 확인한 뒤 결정한다.

### P2 — 스키마 타입·성능·운영 작업의 기준을 보강할 수 있다

- Supabase 클라이언트에 생성된 `Database` 타입을 적용하지 않았고 여러 응답을 `any`로 매핑한다. 기준 스키마 복원 뒤 생성 타입과 RPC 입출력을 함께 관리하면 필드 누락을 더 일찍 발견할 수 있다.
- 관계 인덱스는 저장소에 있지만, `user_id`로 목록을 필터하고 정렬하는 인덱스와 `project_citations(citation_id)` 역방향 인덱스의 운영 존재 여부는 미확인이다. Advisor와 실제 읽기 쿼리의 계획을 본 뒤 추가한다. 큰 문자열 순서 키에는 기존 B-tree 길이 한계가 있어 무조건 원문 정렬 인덱스를 추가하지 않는다.
- 운영 로그·느린 쿼리·자동 VACUUM·연결 수·디스크 경보를 확인한다. 문장·메모 내용이 로그에 남지 않도록 한다.
- 책 순서 트리거는 `auth.uid()`를 요구한다. 격리 DB의 일반 관리자 문맥에서는 책 항목 INSERT가 `42501`로 거절됐다. 사용자 세션 없는 백엔드 일괄 가져오기·보정의 별도 계약이 필요하다. 이 점만으로 트리거를 해제하거나 RLS를 약화하지 않는다.

## 운영에서 결과를 얻는 방법

1. Supabase 대시보드의 대상 프로젝트 → **SQL Editor → New query**에서 [health-check.sql](../../supabase/audit/health-check.sql) 전체를 붙여 넣고 실행한다. 결과는 `database_health` 한 칸의 JSON이다. 개인 기록의 내용은 반환하지 않는다. 관리자의 전체 읽기 권한이 없는 경우 RLS가 집계를 필터할 수 있으므로 결과의 `inspected_role`도 확인한다.
2. **Advisors → Security / Performance**의 경고와 **Database → Backups**의 활성 여부·최근 백업 날짜를 확인한다. Auth·요금제·SMTP·PITR은 이 SQL만으로 확인할 수 없다.
3. SQL이 없는 테이블/함수 또는 제한 시간으로 실패하면, 성공으로 간주하지 않는다. 대상 프로젝트·적용 이력 또는 DB 부하를 확인한다. 운영 데이터를 임의 수정해 결과를 0으로 맞추지 않는다.

psql 연결을 사용할 때는 읽기 전용 트랜잭션에서 파일을 실행하고 `statement_timeout=15s`, `lock_timeout=2s`를 지정한다. SQL Editor에서는 한 SELECT만 실행한다. SQL에 쓰기 작업은 없다.

이 도구는 운영 URL·키·로그인 정보를 읽지 않는다. 먼저 기준 SQL과 후속 마이그레이션의 재구성 실패를 기록한다. 이어 **로컬 역사적 fixture**로 빠진 인용문 FK·페이지 정렬 필드와 권한 강화 파일에 필요한 3개의 자리 표시자 트리거 함수를 추가한 DB에서 후속 22개 마이그레이션과 선택한 불변식을 검증한다. 자리 표시자 함수의 실제 운영 본문이나 전체 운영 스키마를 재현했다고 주장하지 않는다. JSON의 예상 취약 상태는 점검 발견 사항이므로 실행 성공을 전체 안전 판정으로 해석하지 않는다.

확인한 결과: 계정 간 읽기 격리, 복합 FK·양쪽 소유권 정책, 익명 이메일 RPC 제한, 동시 RPC 생성의 단일 ID, 두 연결의 책 순서 충돌 거절, 중복 본인 저자·직접 생성 중복·메모 덮어쓰기·같은 계정 출처 불일치 재현. 점검 SELECT도 실제 읽기 전용 트랜잭션에서 실행했다. 이전 PGlite의 단일 연결 검증과 별도로 이번에는 실제 PostgreSQL 두 연결을 사용했다.

## 권장 진행 순서

1. 운영 읽기 결과와 Advisor·백업 상태를 확보하고 실제 데이터의 무결성을 집계한다.
2. 기준 스키마·복구 경로와 서버 스키마 타입을 정리한다.
3. 목록 조회의 완전성과 원자적 출처 생성·프로젝트 순서 저장을 보장한다.
4. 메모·편집의 충돌 버전과 부족한 불변식을 데이터 보존 방식으로 추가한다.
5. 실행 계획에 근거한 인덱스와 운영 경보·내보내기·복원 연습을 보강한다.

현재 변경은 조사 기록과 점검 도구다. 운영 DB 마이그레이션·제약 추가·백업 정책 변경은 실행하지 않았다.
